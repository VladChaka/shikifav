# 07 — Листинг Chrome Web Store

Рабочий файл фазы 9: готовые тексты, которые вставляются в форму консоли разработчика, и решения по ним. Политика конфиденциальности живёт отдельно — `PRIVACY.md` в корне; она опубликована на `https://shikifav.chakalabs.com/` (закрыто 2026-07-31, подробности — «Открытые вопросы»), и этот же адрес стоит в листинге.

**Порядок самой подачи — в `docs/08-submission-runbook.md`.** Здесь — что вставлять, там — в каком порядке и чем проверять.

## Single purpose (одно назначение)

Магазин требует, чтобы у расширения было одно назначение, описанное одной фразой.

> Управление личными списками аниме, манги и ранобэ на Shikimori: поиск тайтлов, добавление в список, смена статуса, оценки и отметка просмотренных серий — без открытия сайта.

Всё остальное в расширении (календарь онгоингов, экран связанных тайтлов, контекстное меню, страница настроек, раздел поддержки) обслуживает это же назначение и отдельной функциональностью не является.

**Про экран связанных тайтлов (фаза 12) — сама фраза назначения не меняется.** Он не показывает ничего сверх того, что уже есть в результатах поиска (постер, название, год, мой статус), а его единственные действия — «положить в список» и «сменить статус», то есть ровно те, что перечислены в назначении; это способ найти следующий тайтл, а не второе назначение. Формулировка выше уже уехала в магазин, и правка этого поля — повторное ревью: расширять её на «связанные» нет ни повода, ни выгоды.

**Про счётчик и уведомления (фаза 11) — фраза назначения тоже не меняется.** Счётчик показывает, у скольких тайтлов ИЗ ЭТИХ ЖЕ списков есть неотмеченные вышедшие серии, а уведомление зовёт сделать то самое действие, что уже названо в назначении, — отметить серию. Ни одного нового объекта, ни одной новой операции над данными пользователя они не вводят: это напоминание об управлении списками, а не второе назначение. Поле в консоли не трогаем — его правка означает повторное ревью и стоила бы дороже любой выгоды от уточнения.

## Обоснование разрешений

Формулировки для поля «Justification» по каждому пункту. Пишем по одной причине на разрешение и без общих слов — ревьюер проверяет, что разрешение действительно нужно заявленному назначению.

### `identity`
> Вход выполняется через официальную авторизацию Shikimori (OAuth 2.0) в окне `chrome.identity.launchWebAuthFlow`. Другого способа получить доступ к спискам пользователя у API нет. Разрешение используется только для этого окна; адрес электронной почты и профиль Google не запрашиваются.

### `storage`
> Хранит в браузере пользователя токены доступа Shikimori, настройки расширения и кэш последних результатов, из которого popup рисует первый кадр без запроса к сети. Данные не покидают устройство.

### `declarativeNetRequestWithHostAccess`
> Правила API Shikimori требуют, чтобы каждый запрос нёс заголовок `User-Agent` с именем зарегистрированного приложения; без него сервер блокирует доступ. Chrome не позволяет задать `User-Agent` из `fetch()` в service worker — он молча заменяет значение, — поэтому заголовок подставляется одним динамическим правилом `modifyHeaders`, действующим только на запросы к `shikimori.one` и `shikimori.io`. Выбран вариант `...WithHostAccess`, а не полный `declarativeNetRequest`: он не даёт прав сверх уже запрошенных host_permissions.

Это разрешение выглядит для ревьюера подозрительнее остальных — оно про модификацию сетевых запросов. Поэтому в обосновании важно, что правило одно, оно только добавляет заголовок и ограничено двумя доменами; при вопросах ссылаться на `src/lib/api/user-agent-rule.ts`.

### `contextMenus`
> Добавляет один пункт меню, появляющийся при выделении текста на странице: «Найти „…“ на Shikimori». По клику выделенный текст подставляется в поиск расширения.

### `alarms`

> Один периодический будильник, `shikifav-episode-watch`, с периодом 30 минут. По нему расширение спрашивает у API Shikimori, не выросло ли число вышедших серий у онгоингов из списков пользователя, — иначе счётчик на иконке обновлялся бы только в момент, когда пользователь и так открыл расширение. Других будильников расширение не создаёт; разрешение не даёт доступа ни к данным, ни к вкладкам, ни к сети. Будильник снимается, когда функция выключена в настройках, и не делает ни одного запроса у неавторизованного пользователя.

Предупреждения у этого разрешения нет ([permission warnings](https://developer.chrome.com/docs/extensions/reference/permissions-list)), поэтому обновление с ним не отключает расширение у установленной базы (docs/06, решение 2 фазы 11). При вопросах ссылаться на [src/lib/episode-watch.ts](../src/lib/episode-watch.ts): период — одна константа, тик выходит до сети в двух случаях (функция выключена, в storage нет `auth`).

### `notifications` — в `optional_permissions`, а не в `permissions`

> Показывает системное сообщение о вышедшей серии тайтла из списков пользователя: название тайтла и номер серии, без кнопок. Клик закрывает сообщение и открывает вкладку со страницей этого тайтла на Shikimori — на домене, который уже заявлен в host_permissions; адрес приходит в ответе API и перед открытием сверяется со списком доменов расширения, чужой не открывается. За одну фоновую проверку показывается не более трёх сообщений, сводного уведомления нет. Разрешение объявлено необязательным и запрашивается только по нажатию кнопки «Разрешить уведомления» на странице настроек — без него расширение полностью работоспособно, включая счётчик на иконке. Показ идёт локально, средствами Chrome; наружу уведомление ничего не передаёт.

Оно единственное из двух несёт предупреждение «Display notifications», а предупреждение в обновлении отключает расширение у всех, кто уже его поставил, до явного согласия — отсюда `optional_permissions` (решение 2 фазы 11). Поле обоснования под него в консоли **не сверено с формой** — необязательные разрешения там раньше не заявлялись. Проверить при подаче: если отдельного поля не окажется, абзац выше уходит в обоснование `alarms` вторым предложением, а не выбрасывается: ревьюер видит `optional_permissions` в манифесте и спросит про него в любом случае. При вопросах — [src/lib/episode-notifications.ts](../src/lib/episode-notifications.ts): гейт двойной (настройка пользователя и `permissions.contains`), текст уведомления санитайзится до показа, кнопок в уведомлении нет.

**Клик ведёт на страницу тайтла на Shikimori, а не в расширение** (решение владельца 2026-08-17, docs/06 Ф11-16). Для формы отсюда следует ровно два факта, и оба стоит держать наготове: новых разрешений это не требует — `tabs.create({ url })` работает без permission `tabs` (комментарий в [wxt.config.ts](../wxt.config.ts)), — и новых хостов тоже: вкладка открывается на одном из двух доменов Shikimori, уже заявленных в `host_permissions`. Адрес берётся из ответа API (поле `url` в опросе, решение Ф6-26 — адреса не собираются в коде), поэтому перед `tabs.create` он проходит через `shikimoriHref()` в [src/lib/external-url.ts](../src/lib/external-url.ts): адрес разбирается парсером, а не префиксом, и пропускается, только если его origin — один из `ORIGINS`. Подменённый ответ Shikimori увести этот клик на чужой сайт не может.

### `host_permissions` — все три хоста, ОДНО поле в консоли, потолок 1000 символов

**Консоль не даёт поля на каждый хост.** У остальных разрешений полей столько же, сколько разрешений, а host permissions делят одно — «Обоснование (Разрешение на доступ к хостам)», и в нём **1000 символов на все три адреса сразу** (сверено с консолью 2026-08-11). Раздельные тексты ниже в это не влезают: 245 + 1100 = 1345.

**Хуже того, в опубликованном листинге текст обрезан.** Поле показывает `1 000/1 000`, и последняя фраза кончается на полуслове «…идентификатор установки удаля». То есть обоснование, которое видит ревьюер, оборвано — и это состояние действующей версии 1.0.1, а не следствие фазы 12.

**Вставлять в поле ровно это (990 символов вместе с пустой строкой между абзацами, запас 10):**

> https://shikimori.one/* и https://shikimori.io/* — API Shikimori: поиск, чтение списков, изменение статусов, оценок и прогресса. Домены менялись, поддерживаются оба; действующий выбирается в настройках. Пока пользователь вошёл и включён счётчик новых серий, расширение раз в 30 минут само запрашивает его онгоинги в фоне; без входа или с выключенной функцией фоновых запросов нет.
>
> https://www.google-analytics.com/* — анонимная статистика (Measurement Protocol GA4). Только обезличенные события: открытие popup с вкладкой; поиск с каталогом; добавление записи с типом и статусом; изменение записи с видом поля; удаление записи; отметка серии со способом; открытие календаря; открытие связанных с типом; вызов контекстного меню; изменение настройки с именем (тема и домен — со значением); ошибка API с видом и кодом; версия и случайный id установки. Поисковые запросы, названия и id тайтлов, аккаунт и токены не уходят. Отключается в настройках: тогда запросов нет, идентификатор удаляется.

**Переписано в фазе 11 (2026-08-17), и это не косметика.** В первый абзац обязана была войти фраза про фоновый опрос раз в 30 минут: запросы к Shikimori теперь идут и без участия пользователя, а обоснование, которое об этом молчит, расходится с политикой конфиденциальности — это ревьюер сверяет прямо. Фраза стоит 178 символов вместе с пробелом перед ней, а запаса было три, поэтому **ужат абзац про GA4**: убраны раскрытия скобок, уже названные в самих событиях (`(аниме/манга/ранобэ)`, `(статус, оценка, прогресс)`, `(кнопка или ввод номера)`), «идентификаторы» сокращены до `id`, «Статистика отключается» — до «Отключается». Итог: 380 + 2 + 608 = **990**.

Все одиннадцать событий закрытого union по-прежнему названы — перечень сверен с [analytics-events.ts](../src/lib/analytics-events.ts) 2026-08-17, фаза 11 в него ничего не добавила (фоновый тик и уведомления не шлют событий вовсе, docs/06 Ф11-12). **Потолок 1000 символов ограничивает и словарь событий, и описание фоновой работы:** запаса десять символов, поэтому следующее событие в union или второй фоновый сценарий потребуют ужать соседей. Считать так же, как здесь: длина первого абзаца + 2 (перевод строки и пустая строка) + длина второго. Проверять длину перед вставкой, а не после.

Из поля сознательно **не** вошла фраза «фоновая проверка серий событий не шлёт» — на неё не хватило 39 символов. Она не про хосты: место для неё — раздел «Раскрытие данных» ниже и `PRIVACY.md`, где она и записана.

Развёрнутые обоснования по каждому хосту ниже — они длиннее поля и служат объяснением решения, а не текстом для консоли.

#### Развёрнуто: `https://shikimori.one/*`, `https://shikimori.io/*`
Адреса API Shikimori, к которому обращается расширение: поиск, чтение списков пользователя и изменение статусов, оценок и прогресса. Домены сайта исторически менялись, поэтому поддерживаются оба, а действующий выбирается в настройках расширения.

С фазы 11 к этим же адресам идёт и **фоновый опрос**: пока пользователь вошёл и включён счётчик новых серий, раз в 30 минут запрашивается список онгоингов из его списков (`id`, название, число вышедших серий, прогресс) — по нему рисуется число на иконке и решается, показывать ли уведомление. Новых хостов это не добавляет и объём запрашиваемого не расширяет: те же списки того же пользователя, что и при открытом окне. Отличается инициатор — будильник, а не клик, — и это единственная причина, по которой фраза о нём обязана стоять и в поле консоли, и в `PRIVACY.md`.

#### Развёрнуто: `https://www.google-analytics.com/*`
> Отправка анонимной статистики использования через Measurement Protocol GA4: какие функции расширения используются. Передаются только обезличенные события — вкладка, на которой открылось расширение; факт поиска и его каталог (аниме/манга/ранобэ); добавление записи с её типом (аниме/манга) и статусом; вид изменённого поля (статус, оценка или прогресс); факт удаления записи; отметка серии с указанием способа — кнопкой «+1» или вводом номера; открытие календаря; открытие экрана связанных тайтлов с типом тайтла, от которого он открыт (аниме/манга), — без названия, идентификатора и числа связей; использование пункта контекстного меню; имя изменённой настройки, а для темы и домена API — ещё и выбранное значение (переключение самой статистики не сообщается); вид ошибки обращения к API и её HTTP-код; версия расширения и случайный идентификатор установки. Поисковые запросы, названия и идентификаторы тайтлов, данные аккаунта и токены не передаются. Статистика отключается в настройках расширения; в выключенном состоянии запросы к этому адресу не отправляются, а идентификатор установки удаляется.

Перечень сверен с закрытым union `AnalyticsEvent` в [src/lib/analytics-events.ts](../src/lib/analytics-events.ts) 2026-08-10: одиннадцать событий (одиннадцатое — `related_opened`, добавлено в фазе 12), ни одного лишнего параметра. Меняется union — правится этот абзац, иначе обоснование в форме перестаёт совпадать с кодом.

Про этот пункт в форме придётся отвечать и во вкладке Privacy practices — там ответ про сбор данных меняется на «да» (см. ниже). Расхождение между обоснованием здесь и сертификацией там ревьюер увидит сразу.

#### GA4-свойств теперь два, и это не ошибка настройки (подключено владельцем 2026-08-11)

В консоли магазина, на вкладке «Store listing», включены «Дополнительные показатели» — встроенная интеграция Chrome Web Store с Google Analytics. **Она не имеет отношения к обоснованию выше.** Различать их придётся каждый раз, когда речь заходит про «нашу аналитику», поэтому:

| | Свойство фазы 10 | Свойство магазина |
|---|---|---|
| Название | веб-поток `ShikiFAV extension` | заводится магазином, названо по ID расширения |
| Кто собирает | **расширение**, из background через Measurement Protocol | **сам магазин**, на своей странице листинга |
| Что меряет | чем пользуются те, кто уже установил | сколько человек увидели карточку и какая доля установила |
| События | закрытый union из [analytics-events.ts](../src/lib/analytics-events.ts) | `page_view`, `session_start`, `first_visit`, `user_engagement`, `install`, плюс UTM-метки |
| Выключается | переключателем в настройках расширения | кнопкой «Отключить Google Аналитику» в консоли |
| Хранение | по умолчанию свойства | **два месяца**, данные обезличены и агрегированы |

**На листинг, разрешения и раскрытие данных это не влияет, и трогать их не нужно.** Собирает Google на собственной странице, по своим правилам: кода расширения не касается, `host_permissions` не расширяет, в бандл ничего не добавляет. Раскрытие данных описывает то, что делает **расширение**, — интеграция магазина туда не входит.

Практическое следствие одно: **срок хранения два месяца**, то есть сравнить год к году не выйдет. Нужны длинные ряды — выгружать или снимать отчёт раз в пару месяцев вручную.

### Удалённый код
> Не используется. Расширение не загружает и не выполняет код, полученный по сети; весь код входит в пакет.

## Раскрытие данных (вкладка Privacy practices)

Ответы в форме магазина. **Сверить с формулировками формы перед отправкой** — категории там периодически меняются, а неверная сертификация сама по себе нарушение правил.

**Переписано 2026-08-05.** Предыдущая редакция отвечала «нет» почти везде и опиралась на рассуждение «данные остаются локально — значит раскрывать нечего». Это рассуждение **ошибочно**: [user data FAQ](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq) определяет «handle» как «collecting, transmitting, using, or sharing» и прямо требует раскрытия «even when data is processed or stored locally on a user's device». По строгому чтению «да» получают пять категорий из девяти.

| Категория формы | Ответ | Основание |
| --- | --- | --- |
| Информация, позволяющая идентифицировать личность | **да** | Профиль Shikimori в `chrome.storage.local`: ник, числовой id, адрес аватара. Id уходит в запись `user_rates`. |
| Данные для аутентификации | **да** | Access и refresh токены. Они не только хранятся локально, но и уходят в сеть: `Bearer` в каждом запросе и `refresh_token` на `/oauth/token`. |
| Данные о местоположении | **да** | Запрос к GA4 уходит с IP пользователя, и владелец видит страну и регион в отчётах Geo своего свойства. IP прямо назван в определении категории. |
| Действия пользователей | **да** | События об использовании функций в GA4, привязанные к случайному идентификатору установки. |
| Содержимое сайтов | **да** | Выделенный на любой странице текст: читается по клику в контекстном меню, уходит поисковым запросом к Shikimori и кэшируется с результатами в `chrome.storage.session`. |
| Медицинская информация | нет | Таких полей нет ни в хранилище, ни в запросах, ни в словаре событий. |
| Финансовые и платёжные данные | нет | Платежей внутри нет, реквизиты не запрашиваются. `DONATION_METHODS` с 2026-08-06 не пуст (одна запись — Boosty), но это внешняя ссылка: расширение отдаёт адрес наружу и никаких платёжных полей не показывает. |
| Личная коммуникация | нет | Скоуп OAuth — только `user_rates`, content script'ов нет. |

Про «Содержимое сайтов» и «Действия пользователей» — отмечаются **обе**, у них разные основания: выделенный текст против событий GA4. Выбирать между ними не нужно.

**Фаза 11 не добавляет ни одной категории, но меняет основание двух из них (2026-08-17).** Ответы формы остаются прежними — менять в консоли нечего, — а вот почему они «да», теперь звучит иначе:

- **Информация, позволяющая идентифицировать личность** и **Данные для аутентификации**: до фазы 11 всякое чтение списков и всякое использование токена случалось в ответ на действие пользователя. Теперь фоновый будильник раз в 30 минут читает онгоинги из его списков и подписывает запрос его токеном **без участия пользователя и при закрытом окне расширения**, а результат (id тайтлов, число вышедших серий, прогресс) оседает в `chrome.storage.local` до выхода из аккаунта, до кнопки «Очистить кэш» или до выключения счётчика. Категории те же, объём тот же, инициатор — другой; политика обязана называть это прямым текстом, и называет («Куда уходят запросы», «Что хранится в браузере»).

Два вывода, чтобы их не выясняли заново:

1. **Показ уведомления ничего не собирает и никуда не передаёт.** Это вывод на экран средствами ОС — не «collecting, transmitting, using, or sharing» из [user data FAQ](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq). Данные, которые в нём видны (название тайтла и номер серии), уже раскрыты как чтение списков; новой категории «уведомления» в форме нет и заводить в ответах нечего. Два факта, которые стоит держать в голове, и оба описаны в `PRIVACY.md`, в отдельном разделе «Уведомления о новых сериях»: название уходит в системный центр уведомлений, то есть за пределы браузера, а клик по уведомлению уводит пользователя на страницу тайтла на Shikimori — это переход на сайт, чьи домены уже заявлены, а не передача данных куда-либо ещё.
2. **«Удалённый код — не используется» остаётся верным.** Ни alarm, ни уведомление, ни фоновый опрос не грузят и не выполняют код из сети: опрос — это GraphQL-запрос за данными, текст уведомления собирается из локальных строк, а иконка в нём — ресурс пакета (`/icon/128.png`). Отвечать на этот вопрос по-прежнему «нет».

**Фоновый тик и уведомления не шлют ни одного события статистики** (docs/06, Ф11-12): `measured()` на тик не навешен намеренно — иначе разлогиненный или офлайновый профиль отправлял бы `api_failed` каждые полчаса, а политика обещает «ошибки обращения к Shikimori», а не ошибки нашего будильника. Поэтому строка «Действия пользователей» не приобрела новых оснований со стороны GA4.

Основание для «нет» по здоровью и переписке — **тип данных, а не срок хранения**. Формулировкой «текст стирается сразу» пользоваться нельзя: одноразовый только `pendingSearch`, а сам запрос вместе с результатами оседает в `lastSearch` до закрытия браузера или кнопки «Очистить кэш» ([use-search.ts:161](../src/composables/use-search.ts:161)).

- Продажа третьим лицам, использование не по назначению, оценка кредитоспособности — нет.
- Три обязательные декларации внизу формы (данные не продаются, используются только по заявленному назначению, не используются для кредитоспособности) — подтверждаются: статистика служит развитию расширения и больше ничему.
- Ссылка на политику конфиденциальности — обязательна, см. «Открытые вопросы». Политика **обязана** описывать сбор: с фазы 10 в `PRIVACY.md` есть отдельный раздел, и он — источник правды для этой вкладки.

## Каналы поддержки (решено 2026-07-30)

В листинге есть раздел Support, и вопрос только в том, куда ведёт его ссылка ([Provide user support](https://developer.chrome.com/docs/webstore/user-support)). Вариантов два, включаются они взаимоисключающе: встроенный хаб магазина (тумблер «Поддержка продукта → Доступность» в настройках аккаунта) или свой адрес в поле Support URL.

**Выбран хаб.** Аудитория Shikimori — не разработчики, а Issues требуют аккаунта GitHub; хаб открыт любому, кто уже вошёл в Chrome. Обращения падают во вкладку **User support** у продукта с типом (bug report / feature request / question), статусом и — что важнее всего для отладки — версией расширения, браузером и ОС; на новое обращение приходит письмо, если включено уведомление «Возникла проблема с поддержкой товара».

Репозиторий указывается отдельным полем **Homepage URL**, не Support URL: тот, кому нужны Issues, дойдёт до них оттуда.

Оговорка из документации: **ответ разработчика пользователя не уведомляет** — он увидит его, только вернувшись в листинг. Публичная польза остаётся: остальные видят, что на обращения отвечают.

Если позже появится своя площадка (Google Group, форма), порядок обратный: вписать Support URL и **выключить** тумблер, иначе хаб перебивает ссылку.

## Пожертвования: что говорит магазин (проверено 2026-07-30)

Пожертвование платой за копию не является; главное — не превращать существующую функциональность в платную. §3.4 требует валидный контакт в листинге — это тот же контакт, что и пункт 2 выше.
