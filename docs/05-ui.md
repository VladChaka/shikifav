# 05 — UI и производительность

## Принципы
1. Скорость важнее украшений: никаких UI-фреймворков, свой минимальный CSS (бюджет — ниже), системный шрифт (`system-ui`).
2. Плотный компактный интерфейс: popup — рабочий инструмент, не витрина.
3. Тёмная/светлая тема автоматически: `prefers-color-scheme` + CSS-переменные. Настройка `theme` (`system` / `light` / `dark`, Ф6-19) переопределяет систему: `src/lib/theme.ts` ставит `data-theme` на `<html>` (для `system` атрибут снят), а в `src/styles/foundation.scss` тёмные значения применяются из двух мест — `@media (prefers-color-scheme: dark) :root:not([data-theme='light'])` и `:root[data-theme='dark']`, поэтому явный светлый выбор не перебивается тёмной системой. `color-scheme` живёт по тому же правилу: светлое значение стоит на `:root`, обе тёмные ветки его перекрывают, отдельного правила под явный светлый выбор не нужно (Ф6-17). Тема применяется до `mount()` в каждой точке входа — иначе первый кадр мигает системной темой.
4. Все строки интерфейса — русские, собраны в `src/lib/i18n.ts` одним объектом (без библиотек).

## Перфоманс-бюджеты (аудит в фазе 6, но соблюдать с фазы 0)
- JS popup суммарно: **≤ 80 КБ gzip** (Vue runtime ~35 КБ → на код приложения ~45 КБ)
- CSS точки входа (сумма всех её `<link>`, замер `pnpm size`): popup **≤ 5 КБ gzip**, страница поиска **≤ 4,5 КБ**, настройки **≤ 3 КБ**. Факт после чистки Ф6-17: 4,5 / 3,8 / 2,6 КБ gzip (18,6 / 14,0 / 9,4 КБ raw).
- Исходная формулировка «2–4 КБ» относилась к одной точке входа фазы 0 и к трём страницам не подходит. Довести popup до 4 КБ **чисткой уже нельзя**: из его 4,5 КБ gzip ровно 1,0 КБ — цена того, что CSS раздан тремя файлами (`theme` / `use-search-screen` / `popup`), а каждый gzip-поток стартует с пустого словаря. Тем же содержимым одним файлом popup весит 3,6 КБ. Дробление задаёт `cssCodeSplit` Vite через `wxt.config.ts`; объединение — отдельная задача, не чистка стилей.
- Открытие popup → первый осмысленный рендер: **< 150 мс**. Первый осмысленный рендер (FMR) = от `performance.timeOrigin` документа popup до кадра, в котором отрисован реальный контент: шапка с ником **и** карточки/строки, восстановленные из `chrome.storage.session`. Скелет авторизации и пустая оболочка осмысленным рендером не считаются.
- Первый рендер — из кэша `chrome.storage.session` (последний поиск / список / вкладка), сеть догоняет и обновляет
- Постеры: маленький превью-URL, `loading="lazy"`, фиксированные размеры контейнера (без layout shift). Бокс карточки поиска — 60×94, натуральный размер `poster.miniUrl` (Ф6-25: прежние 48×66 не уменьшали картинку, а срезали 12% её высоты). Ассеты никогда не инлайнятся в бандл: `build.assetsInlineLimit: 0` в `wxt.config.ts` — Vite по умолчанию встраивает всё легче 4 КБ, и заглушка постера так съела 9 КБ gzip бюджета popup
- Debounce поиска 300 мс; устаревшие ответы отбрасываются (сравнение requestId)
- Никаких блокирующих запросов при открытии popup: `auth.getState` читает только storage

## Перф-аудит Ф6-12 (2026-07-27) — факт против бюджетов

Стенд: production-сборка `.output/chrome-mv3`, Chrome 150.0.7871.186 (Linux, Xvfb :99 + metacity, отдельный профиль). ### Первый осмысленный рендер (FMR)

Мерялось временной инструментацией в `entrypoints/popup/main.ts` и `App.vue` (`requestAnimationFrame` в момент рендера ветки с контентом + `performance.now()`); после замера инструментация снята, в репозитории её нет. По 10 открытий на режим, значения в мс:

| Режим | медиана | худшее |
|---|---|---|
| тёплый service worker (popup только что открывали) | **50,5** | 56,2 |
| холодный service worker (`ServiceWorker.stopAllWorkers` перед каждым открытием) | **66,5** | 69,3 |
| первое открытие после старта браузера | 77,2 | — |

Разбор тёплого открытия: eval JS popup ≈ 26 мс → ожидание `initTheme()` **1,0–1,6 мс** → mount и первый кадр с контентом. То есть чтение `chrome.storage.local` до `mount()` (цена против мигания темы, Ф6-19) в бюджете практически не видно — около 1 мс, а не десятки. Холодный старт service worker добавляет ~16 мс.

Поправка на процесс рендерера: `chrome.action.openPopup()` нельзя вызвать, не имея открытой страницы расширения, а она держит процесс рендерера тёплым — чего у настоящего «холодного» открытия нет. Отдельный контрольный замер той же страницы во вкладке (6 + 6 открытий, service worker холодный в обоих) дал FMR 82 мс с тёплым процессом против 97 мс с холодным, то есть спавн процесса ≈ +15 мс. Реалистичная холодная оценка popup: **≈ 80 мс медиана, ≈ 85 мс худшее** — примерно вдвое ниже бюджета 150 мс.

### Сетевые запросы при открытии

CDP-сессия на background service worker (`Network` + консоль; отладчик заодно не даёт воркеру уснуть, так что ни один запрос не теряется в перезапуске):
- popup, восстановивший вкладку «Поиск» из кэша: **0 запросов** к API, ни одной строки `[http]`. Страница тянет только превью-постеры карточек (page-level, не API).
- popup, восстановивший вкладку «Мои списки»: ровно **1** запрос `rates.list` (GraphQL) — плановый рефреш `activate()` (docs/06, дополнение фазы 3). Первый кадр к нему не привязан: строки уже отрисованы из `session.lastList`, запрос только обновляет их.

### Что осталось на ручную проверку владельцем
Клик по иконке расширения в панели (программно недоступен), живой аккаунт и настоящие постеры, профиль с обычным набором вкладок и расширений — числа выше сняты на чистом профиле и синтетическом кэше.

## Popup (~380 × 580)

Оболочка popup — без скругления и рамки, фон на `body`. Скруглённый вариант (radius 14px) пробовали 2026-07-27 и откатили решением владельца: настоящей прозрачности окна popup у Chrome нет, углы за радиусом заливаются фоном окна браузера, поэтому скругление читается как рамка вокруг «отрезанных» углов, а не как скруглённая оболочка. `color-scheme` оставлен ради нативных скроллбаров и контролов по теме. Тень из дизайна не переносим — её рисует сам Chrome вокруг окна.

### Экран «не авторизован»
Иконка, один абзац («Войдите, чтобы управлять своими списками»), кнопка «Войти через Shikimori». Ошибка входа — текст + «Повторить».

### Экран «авторизован»
```
┌──────────────────────────────────────┐
│ [ава] nickname                 ⚙  ⎋ │  ⚙ настройки · ⎋ выход
│ [Поиск] [Мои списки] [Календарь]     │  вкладки
│ [поле поиска……………………………………………× ]      │
│ (Аниме) (Манга) (Ранобэ)             │  чипы типа, активный — залит
├──────────────────────────────────────┤
│ [постер] Фрирен…                8.9  │
│          TV · 2023 · вышло           │
│          [ + Запланировано ▾ ]       │  или бейдж моего статуса ▾
│ ──────────────────────────────────── │
│ [постер] …                           │
└──────────────────────────────────────┘
```
- Не в списке: primary-кнопка быстрого добавления (1 клик), `▾` раскрывает остальные статусы. Статус кнопки — настройка `quickStatus` (по умолчанию «Запланировано»), подпись собирается как `'+ ' + statusLabel(quickStatus, media)`: на карточке манги/ранобэ тот же статус читается по-книжному («+ Читаю», «+ Прочитано»).
- В списке: бейдж текущего статуса, `▾` — сменить статус / удалить из списка.
- **Постер и название — ссылки на страницу тайтла на сайте** (Ф6-26), в новой вкладке. Адрес берётся из поля `url` в ответе GraphQL: он приходит абсолютным и на том домене, с которого пришёл ответ, поэтому настройка домена учитывается сама и пути в коде не собираются. В `href` попадает только `https://`-значение (`src/lib/title-url.ts`) — значение серверное и переживает в session-кэше, поэтому трактуется как недоверенный ввод; запись без `url` (кэш от старых сборок) рендерится обычным текстом, это законное состояние, а не ошибка. Ссылка постера продублирована с названия, поэтому она вне таб-порядка и вне a11y-дерева. Кликается только постер и название: `+1`, оценка и бейдж статуса лежат вне ссылок.
- **Откуда берётся картинка** (Ф6-27), три ступени: постер из GraphQL → если пусто, добор батч-запросом REST на страницу выдачи (до 50 id в запросе — потолок REST `limit`; если пустых постеров больше, id уходят последовательными батчами, как на календаре с его 150 строками, Ф7-14) → локальная заглушка `src/assets/poster-fallback.png`. Пустой постер — не редкость: у тайтлов с рейтингом `rx` GraphQL отдаёт `poster: null`, хотя файлы публично доступны. Батч уходит только при наличии пустых постеров, список рисуется не дожидаясь его, отказ добора молча оставляет заглушку (это не действие пользователя — тоста нет). Заглушка — «404 not found» с сайта, карандашный набросок на белой бумаге: прозрачной её сделать нельзя (линии пропадают на тёмной теме) и инвертировать нельзя (затенённый рисунок даёт негатив), поэтому в тёмной теме она приглушается через `--poster-placeholder-opacity`.
- Обновления оптимистичные; при ошибке — откат + тост.
- Поле поиска: во всю ширину, нативный крестик очистки скрыт, вместо него своя кнопка «×» (серая, muted; hover — основной цвет текста), очистка возвращает фокус в поле.
- Тип (Аниме/Манга/Ранобэ) — тот же ряд чипов, что во вкладке «Мои списки», под полем поиска.

### Вкладка «Мои списки»
- Фильтры — два ряда pill-чипов (общий компонент `ChipGroup`, `role=radiogroup`, переключение в 1 клик): тип (Аниме/Манга/Ранобэ, 3 чипа без точек, активный — нейтральная заливка `--color-surface`; акцентная заливка не используется, в светлой теме акцент совпадает с цветом статуса «Смотрю») и статус (6 чипов с цветными точками в 2 строки, активный — тинт своего статуса; стартовый — настройка `defaultListStatus`, по умолчанию «Смотрю»).
- Строка: постер, название, `7 / 12 эп.` + кнопка `[+1]`, моя оценка (клик → выбор 0–10), бейдж статуса (клик → StatusMenu: сменить статус / удалить — добавлено по итогам smoke фазы 3, решение владельца 2026-07-23). Строка, чей новый статус не соответствует фильтру, уходит из списка после подтверждения сервером.
- `[+1]` показывается для watching/rewatching. Достигли максимума → inline «→ Просмотрено?» (Да / позже).
- Порционная подгрузка: limit 30, кнопка «Ещё».

### Вкладка «Календарь» (фаза 7)
Расписание онгоингов из моих списков «Смотрю», «Пересматриваю» и «Запланировано» (docs/06, «Статусы календаря»). Источник правды по виду — карточка `screens/calendar` в Claude Design. Третья подпись помещается в 380 px без сокращений (108,7 px под текст против 86,9 px у самой широкой), геометрия `TabBar` не менялась.

```
┌──────────────────────────────────────┐
│ Сегодня                              │  липкий заголовок дня
├──────────────────────────────────────┤
│ [постер] Re:Zero…             16:00  │
│          Серия 9 из 16       ● Смотрю│
│          вы на 5-й из 8 вышедших     │
│ ──────────────────────────────────── │
│ Дата не объявлена                    │
└──────────────────────────────────────┘
```
- Строка: постер 42×58 (как в «Моих списках»), название одной строкой с многоточием — ссылка на страницу тайтла (постер дублирует её и потому вне таб-порядка, как в `RateRow`), время справа своей колонкой (`tabular-nums`; разметка `<time datetime>`: в атрибуте — момент из API, в тексте — местное время). Ниже — «Серия N из M», справа в той же строке бейдж моего статуса, под ними строка отставания.
- Бейдж статуса обязателен: в выдаче лежат три статуса сразу, без него «смотрю» и «собираюсь смотреть» неразличимы. Это `<span>`, а не кнопка — вкладка **read-only**: `[+1]`, оценка и смена статуса живут в «Моих списках» (docs/06, объём фазы 7), поэтому ни каретки, ни меню, ни hover у бейджа нет.
- «из N» опускается, когда общее число серий неизвестно (`episodes: 0` у долгожителей вроде One Piece) — «Серия 1147»; при противоречивых данных (вышло больше, чем объявлено) номер серии не пишется вовсе.
- Строка отставания — только у «Смотрю»/«Пересматриваю» и только при реальном отставании: у «Запланировано» его не бывает по определению. При нулевом прогрессе текст свой («вы ещё не начали») — общая формула дала бы «вы на 0-й из 3 вышедших».
- Группировка по локальным дням: липкие заголовки «Сегодня» / «Завтра» / `пн, 3 августа` (регистр — как отдал `Intl`), внутри дня по времени по возрастанию, группа «Дата не объявлена» последняя и ничем, кроме текста, не выделена. Сегодняшний эфир остаётся под «Сегодня» и после того, как прошёл; дата раньше начала сегодняшнего дня означает, что сервер не сдвинул серию, — такая строка уходит в группу без даты.
- **Ряда чипов типа нет** — ни трёх, ни одиночного «Аниме»: календарь anime-only (у `Manga` нет `nextEpisodeAt`, docs/03), а чип обещал бы выбор, которого не существует.
- Состояния — те же четыре: `skeleton` (`SkeletonList`, заголовков дней в нём нет), данные, `empty` (`EmptyState` с иконкой 📅 вместо лупы: лупа на вкладке без поиска читается как «ничего не нашлось по запросу»; текст объясняет, что календарь только про аниме), `error` (`ErrorState` + «Повторить»). Своих текстов ошибок вкладка не заводит — `apiErrorMessage()` как везде.
- Загрузка ленивая: popup, открытый на другой вкладке, календарь не запрашивает вовсе; запрос уходит при первом показе вкладки и повторяется при каждом следующем (как `activate()` «Моих списков»). Возврат на вкладку рисует строки сразу из `session.lastCalendar`, скелетон — только когда показывать нечего; кэшируются строки, а не расписание (docs/02).

### Состояния данных (обязательны для каждого списка)
`skeleton` (3–5 строк-заглушек) → данные | `empty` («Ничего не найдено») | `error` (текст по `ApiError.kind` + «Повторить»).

Отдельный случай (фаза 2): запись user_rate не прошла из-за отозванного доступа → неблокирующее предупреждение у места действия «Нет доступа на редактирование — войдите заново». Проактивно (при открытии popup, до попытки редактирования) не показывается — обнаружение ленивое (docs/04 §3, решение владельца 2026-07-23).

## Options page (entrypoints/options, Ф6-3)

Расчётные 880 (216 сайдбар + 28 + 560 меры чтения) пробовали и **отвергли решением владельца 2026-07-28**: на настольном мониторе узкая колонка в широком окне выглядит потерянной. Мера чтения остаётся 560 px, но живёт на самих блоках настроек (`.opt__hint`, ряды чипов), а не на колонке страницы — панель шире меры, текст в ней не растягивается. Раскладка — grid, поэтому версия стоит последней в DOM и попадает в нижнюю левую ячейку без дублирования элемента.

| Раздел | Что внутри |
|---|---|
| **Вид** | `theme` — системная / светлая / тёмная; `titleLang` — русские / ромадзи (что показывать первой строкой карточек и строк списка) |
| **Поведение** | `startTab`; `quickStatus` (те же 6 статусных чипов, что фильтр «Моих списков»); «Фильтры по умолчанию» — `defaultSearchType` и `defaultListStatus` двумя подписанными рядами внутри одного блока |
| **Аккаунт и данные** | домен API (`XSelect`, `shikimori.io` первым — рабочий); «Очистить кэш» (сбрасывает `storage.session`, тост «Кэш очищен»); «Выйти» — только у авторизованного, danger-вариант ghost-кнопки |

Порядок разделов намеренный: что меняется один раз и видно сразу → что меняет привычку открывать popup → что чего-то стоит (домен завершает сессию, «Выйти» тоже).

Кнопки «Сохранить» нет: каждый контрол пишет storage сразу, запись возвращается в UI через подписку `use-settings` — локального зеркала, способного разъехаться с хранилищем, у контролов нет. Единственное исключение — домен API: он идёт сообщением `settings.setOrigin` в background (logout → запись origin, docs/02), после ответа страница перечитывает состояние авторизации, иначе продолжала бы предлагать «Выйти». Предупреждение «Смена домена завершает сессию» стоит в подсказке **до** клика и выделено жирным — диалога подтверждения нет.

Версия — не раздел, а подпись в подвале сайдбара: видна из любого раздела. Приходит пропом из точки входа (`runtime.getManifest().version`), сам компонент к runtime не обращается и потому монтируется в тестах.

Пол панели: `min-height: 460px` — высота самого высокого раздела («Поведение»), так что переключение разделов не двигает страницу; короткие разделы добирают пустотой.

**Узкое окно (≤ 620 px).** Сайдбар поднимается горизонтальным рядом табов над панелью; вертикальная линия уходит, её роль берёт линия под рядом; «Аккаунт и данные» подменяется на «Аккаунт» (обе подписи лежат в разметке, переключает CSS — слушатель resize тут ничего не даёт); версия уезжает под панель, селект домена растягивается во всю ширину. Иконки вместо подписей отвергнуты: три русских слова помещаются, а своего набора иконок у расширения нет.

**ARIA-контракт табов** (паттерн APG): `role=tablist` + `aria-orientation=vertical` с меткой раздела, кнопки `role=tab` с `aria-selected`, панель `role=tabpanel` с `aria-labelledby` активного таба. В DOM живёт только активная панель, поэтому `aria-controls` есть лишь у выбранного таба. Roving tabindex: tabbable только выбранный (`tabindex=0`, остальные `-1`) — весь таб-лист это одна остановка Tab; ↑/↓ двигают выбор вместе с фокусом и зацикливаются на краях, Home/End — на первый/последний. Активная полоска слева всегда в потоке (прозрачная в покое), чтобы выбор не сдвигал подпись. Активный раздел не запоминается: страница всегда открывается на «Вид», ключа storage под это не заводим.

### Поведенческие настройки (Ф6-20)
Схема и дефолты — в docs/02-architecture.md; дефолт каждой повторяет поведение до её появления.

| Настройка | На что влияет |
|---|---|
| `startTab` | вкладка при открытии popup: `last` — восстановить `session.lastTab`, `search`/`lists`/`calendar` — всегда заданная. Кэш `lastTab` пишется в любом случае: на нём живёт режим `last`. Значение из чужой сборки (и в настройке, и в кэше) отбрасывается — popup открывается на «Поиске», а не в окне без активной вкладки (Ф7-9) |
| `quickStatus` | статус кнопки быстрого добавления на карточке поиска (и её подпись) |
| `defaultSearchType` | стартовый тип поиска |
| `defaultListStatus` | стартовый фильтр статуса в «Моих списках» |

Приоритет стартового состояния (`use-search`, `use-lists`): **действие пользователя** (он уже переключил руками, пока читалось storage) > **session-кэш прошлой сессии** (тип поиска / фильтр списка — это свежее намерение, и на нём же держится мгновенный первый рендер) > **настройка** > встроенный дефолт. Настройки и кэш читаются одним `Promise.all`, поэтому результат не зависит от того, какое чтение успело первым. Исключение — поиск из контекстного меню: там выделение приходит без типа, и настройка перебивает кэш (см. ниже).

## Поиск из контекстного меню (фаза 5)
Основной сценарий (решение владельца 2026-07-27): пункт меню **открывает popup**, а не новую вкладку. Background кладёт выделение в `session.pendingSearch` и вызывает `action.openPopup()`; popup при монтировании забирает ключ (одноразовый, удаляется сразу), включает вкладку «Поиск» (сильнее настройки `startTab` — popup открыт ради этого запроса) и выполняет запрос без debounce — пользователь уже «набрал» текст выделением. Тип поиска принудительно ставится в `defaultSearchType`: выделение не несёт типа, а восстановленный из кэша прошлой сессии («Ранобэ» на название аниме) молча ответил бы нулём результатов. До Ф6-20 тип здесь был жёстко «Аниме»; теперь у пользователя есть явная настройка типа, и она главнее (решение владельца 2026-07-27).

Неавторизованный пользователь: ключ `pendingSearch` **не удаляется**, пока запрос не выполнился под токеном. Вход открывает окно OAuth, и Chrome закрывает popup вместе с ним — ключ, съеденный при чтении, потерял бы запрос насовсем, и пользователю пришлось бы заново выделять текст. Поэтому ключ живёт до первого успешного открытия под авторизацией: popup, открытый после входа, сам доигрывает запрос. Если вход произошёл, не закрыв popup, запрос повторяется в том же окне (та же схема, что на странице поиска).

## Страница поиска (entrypoints/search, фаза 5) — запасной путь
Полноэкранная версия вкладки «Поиск» с переиспользованием тех же компонентов, `?q=<текст>` в URL. Открывается только если popup открыть не удалось (нет активного окна, Chrome старше 127, отказ политики) — иначе клик по пункту меню не дал бы вообще ничего.

Дизайн — карточка `screens/search-page` в Claude Design.
- Только поиск: вкладок и «Моих списков» на странице нет. Компоненты те же, что в popup (`UserHeader`, `SearchTab`, `TitleCard`, `SkeletonList`, `EmptyState`, `ErrorState`, `Toast`, `LoginScreen`), новых не вводим — страница владеет только своей обёрткой.
- Оболочки нет: страница занимает всю вкладку, без рамки, радиуса и фиксированных размеров. Шапка — полоса во всю ширину, её содержимое и контент выровнены по колонке `max-width: 720px` по центру.
- Результаты и состояния лежат в боксе с рамкой и радиусом 10px. Бокс НЕ обрезает содержимое: `overflow: hidden` срезал бы открытый `StatusMenu` последней карточки (меню флипается вверх у края вьюпорта, а не бокса).
- Тип поиска при открытии с `?q=` — `defaultSearchType` (до Ф6-20 было жёстко «Аниме»): из контекстного меню тип неизвестен, а восстановленный из кэша «Ранобэ» молча дал бы 0 результатов по названию аниме. Первый запрос уходит синхронно, ещё до чтения storage (первый кадр не ждёт диска), и прилетевшая через тик настройка перезапускает тот же запрос, только если тип реально другой: профиль с дефолтом лишнего запроса не платит, а на не-дефолтном ответ первого запроса отбрасывается по requestId и на экран не попадает. Страница, открытая без `?q=`, стартового типа не форсит — там работает обычный приоритет «кэш > настройка».
- Выделение обрезается до 100 символов, переводы строк схлопываются в пробел (`sanitizeQuery`); пустое выделение открывает страницу без `?q=` — подсказка и автофокус в поле.
- Неавторизован: экран входа по центру колонки, шапки нет. Запрос из `?q=` уходит сразу, не дожидаясь чтения состояния авторизации (токен подставляет background), а запрос, ушедший до входа, после успешного логина повторяется ровно один раз.
- Session-кэш `lastSearch` общий с popup: поиск со страницы становится последним поиском и в popup — так бейджи статусов остаются согласованными между контекстами.

## Слои стилей (после Ф6-17)
Глобального CSS ровно два файла, и каждая точка входа подключает только то, что реально рисует:

| Файл | Что внутри | Кто подключает |
|---|---|---|
| `src/styles/foundation.scss` | токены темы, палитры статусов `.st-*`, reset, интерактивные умолчания `button` | popup, поиск, настройки |
| `src/styles/badge.scss` | пилюля `.badge` (`.dot`, `.car`, тёмная заливка) | popup, поиск — настройки бейдж не рисуют |

Интерактивные умолчания в foundation: любая `<button>` — указатель, при `:disabled` гаснет до `opacity: .6`, при `:focus-visible` получает акцентное кольцо `2px` с отступом `2px`. Компоненты переопределяют только отличие (более тесный отступ кольца, более глубокое гашение), а отказ — обычный `outline: none` (так делает `XSelect`). До Ф6-17 эти две-три строки повторялись в ~15 правилах компонентов.

Всё остальное — scoped-стили компонентов; общего «утилитарного» слоя нет и не заводим.
