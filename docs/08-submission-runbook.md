# 08 — Рунбук подачи в Chrome Web Store

Порядок действий на день подачи, одним списком. Всё, что нужно решить или прочитать заранее, собрано в шаге 0.

**Здесь нет текстов и обоснований** — они живут в `docs/07-store-listing.md`, и дублировать их сюда нельзя: разойдутся. Этот файл отвечает только на вопрос «что за чем и как понять, что шаг удался».

Главное, что легко сделать не в том порядке: **ключ расширения выдаёт магазин, а не мы.** Поэтому загрузка идёт черновиком, потом ID, потом redirect URI, и только потом публикация. Ошибка здесь ломает вход у всех сразу, и чинится она новой версией — то есть не мгновенно.

## Шаг 0. До дня подачи

Аккаунт разработчика:

- [ ] Аккаунт в [консоли разработчика](https://chrome.google.com/webstore/devconsole) заведён, единоразовый регистрационный взнос оплачен (сумма показывается в самой консоли).
- [ ] **Двухэтапная проверка включена** на этом Google-аккаунте. Это не рекомендация: правила требуют 2SV до публикации и до любого обновления ([2-Step Verification](https://developer.chrome.com/docs/webstore/program-policies/policies)).
- [ ] Почта аккаунта принимает письма извне и не режет их в спам — уведомления об отклонении и снятии приходят только туда ([Notification and Appeals](https://developer.chrome.com/docs/webstore/program-policies/policies)).

Страница «Настройки» издателя (`/devconsole/<ID издателя>/settings`) — заполняется один раз на аккаунт, до создания элемента:

- [ ] **Отображаемое название издателя** — `Chaka Labs` (публично, показывается под названием расширения).
- [ ] **Контактный адрес** — подтверждён по ссылке из письма. Публичный: показывается на страницах расширения.
- [ ] **Отношение к торговле** — «аккаунт не продавца». Продавцом делает продажа внутри продукта, которой у нас нет; выбор «продавец» сделал бы почтовый адрес обязательным и публичным.
- [ ] **Адрес** — не заполнять по той же причине.
- [ ] **Уведомления** — включить все четыре по e-mail. По умолчанию выключены все, а результат ревью приходит именно письмом.
- [ ] **Поддержка продукта → Доступность** — включить (обоснование и альтернатива — docs/07, «Каналы поддержки»).
- [ ] Нажать **«Сохранить»** — страница не автосохраняется.

Решения (без них форму не заполнить):

- [x] **Контактный адрес** — `support@chakalabs.com` (Cloudflare Email Routing на домене проекта, пересылка в личный ящик; отправки нет, только приём). Вписан в `PRIVACY.md` в обеих частях, он же идёт в листинг и закрывает Developer Agreement §3.4. В консоли остаётся подтвердить его по ссылке из письма.
- [x] **Публичный адрес политики** — `https://shikifav.chakalabs.com/`. Собирается из `PRIVACY.md` через `.github/workflows/pages.yml` (копии файла в репозитории нет) и отдаётся GitHub Pages; домен ведёт туда CNAME `shikifav` → `vladchaka.github.io`, обязательно **DNS only**: через прокси Cloudflare сертификат Pages не выпустит. Каждый пуш `PRIVACY.md` в `master` пересобирает страницу.

## Шаг 1. Собрать пакет

```bash
pnpm compile && pnpm lint && pnpm test
pnpm build && pnpm size
pnpm zip
```

- [ ] Все проверки зелёные, бюджеты в норме.
- [ ] Архив на месте: `.output/shikifav-<версия>-chrome.zip`.
- [ ] `version` в `package.json` — та, под которой подаём (для первой подачи `1.0.0`). Каждое следующее обновление требует нового номера, иначе консоль отклонит загрузку.

Проверка, что собралось именно то:

```bash
node -e "const m=require('./.output/chrome-mv3/manifest.json'); console.log(m.version, m.permissions, m.host_permissions, 'key:', 'key' in m)"
```

Разрешения должны совпасть с теми, что обоснованы в docs/07: `identity`, `storage`, `declarativeNetRequestWithHostAccess`, `contextMenus`. Хостов **три**: два домена Shikimori и `https://www.google-analytics.com/*` (фаза 10). Лишнее в этом списке — лишний вопрос от ревьюера.

Отдельно про третий хост: он тянет за собой не только своё обоснование, но и ответ во вкладке Privacy practices — с фазы 10 сбор данных там **«да»** (docs/07). Обоснование и сертификация обязаны сойтись; расхождение ревьюер видит сразу.

## Шаг 2. Черновая загрузка и ID (критический шаг)

1. [ ] **Пересобрать пакет без ключа.** Архив из шага 1 консоль не примет: манифест с полем `key` она отвергает с ответом «Недопустимое поле в файле манифеста: key» (проверено 2026-08-05).
   ```bash
   WXT_MANIFEST_KEY=none pnpm zip
   ```
   Такая сборка входить не умеет — она нужна ровно для того, чтобы магазин выдал ключ. Вернуть ключ на шаге 4.
2. [ ] В консоли: **Add new item** → **Browse files** → этот архив. **Не публиковать**, сохранить черновиком.
3. [ ] Записать **Item ID** из адресной строки консоли.
4. [ ] Вкладка **Package** → **View public key** → скопировать содержимое между `-----BEGIN PUBLIC KEY-----` и `-----END PUBLIC KEY-----`, **убрать переносы строк**.

## Шаг 4. Пересобрать под магазинный ключ и проверить вход

1. [ ] В `.env` заменить значение `WXT_MANIFEST_KEY` на ключ из шага 2.4.
2. [ ] `pnpm build` — сборка упадёт, если переменная пуста; это защита, а не поломка (README §8).
3. [ ] Проверить, что ID сошёлся: загрузить `.output/chrome-mv3` распакованным в `chrome://extensions` и сверить ID карточки с Item ID из консоли. **Не совпало — дальше не идти**, ключ скопирован с переносами или не тот.
4. [ ] **Войти в этой сборке.** Это и есть проверка всего шага: до публикации вход ломается только у вас, после — у всех.
5. [ ] `pnpm zip` — архив для публикации.

## Если что-то пошло не так

**Вход не работает у пользователей после публикации.** Значит ID и redirect URI разошлись — шаг 4.3 пропущен или сделан не тем ключом. Лечится только новой версией: вернуть правильный ключ, собрать, загрузить обновление. Пока оно раскатывается, вход сломан у всех, кто успел поставить.

**Консоль не принимает пакет с нашим `key`.** Шаг 2.2 — собрать с `WXT_MANIFEST_KEY=none`, забрать ключ магазина, вернуться на шаг 4.

**Секрет утёк или приложение №2175 заблокировали.** Перевыпуск секрета ломает обновление токенов у всех установок сразу — это принудительный повторный вход, а не тихая операция (docs/04 §5). Планировать как рутину нельзя.

**Shikimori разрешил public client.** Тогда секрет уходит из сборки: `PKCE_ENABLED` в `src/lib/api/auth.ts` уже реализован, править нужно docs/04 §5 и абзац README §3.
