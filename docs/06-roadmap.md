### Правки по итогам просмотра владельцем (2026-07-27/28)

**Решения, принятые за владельца (отменяются дёшево):** потеря фокуса **отменяет** ввод, а не сохраняет — popup закрывается от любого клика мимо, и сохранение по blur молча записало бы недонабранное «1» вместо «11»; ввод доступен **при любом статусе**, в отличие от `[+1]` (только «Смотрю»/«Пересматриваю») — отметить, где остановился, нужно и в «Отложено», и в «Брошено».

**Реализация:** кликается вся фраза `5 / 11 эп.` (мишень 55,8×20,8 против 7,6 у одной цифры), полем становится только число, `/ 11 эп.` остаётся текстом и подменяется на «макс. N» при недопустимом значении. Высота строки в наборе не меняется (замер: 79,00 → 79,00). `[+1]` и ввод делят `runRowAction`, поэтому блокировка строки, откат и тост — те же; реконсиляция серверного ответа вынесена в общую `applyProgressResult()`.

**DoD дополнения (ручной smoke владельца):** введённое число видно на сайте; на последней серии поведение то же, что у `[+1]`; недопустимое значение не уходит на сервер; ввод в строке манги двигает главы.

**Поведение на последней серии уточнилось по ходу дополнения (2026-07-29), формулировка DoD приведена к факту.** Исходно тут стояло «на последней серии появляется предложение перевести в „Просмотрено“». На аниме с известным числом серий такого предложения **не бывает**: Shikimori переводит тайтл в «Просмотрено» сам (docs/03, проверено PATCH), а `maybeSuggest` (`src/composables/use-lists.ts`) ставит предложение только по **подтверждённому сервером** статусу `watching`/`rewatching` — к моменту ответа он уже `completed`. Предложение остаётся живым там, где сервер сам не переводит (например, прогресс догнали, а статус не сменился). Смена статуса сервером показывается тостом — Ф7-20, тот же факт записан выше в чекбоксе дополнения и ниже в smoke.

2. вкладка **Package** → **View public key** → скопировать содержимое между `-----BEGIN PUBLIC KEY-----` и `-----END PUBLIC KEY-----`, убрать переносы строк;
3. вписать это значение в манифест как поле `key` — тогда локальная сборка получает **тот же ID, что и элемент магазина**;
4. сверить: ID на `chrome://extensions` должен совпасть с Item ID в консоли.

То есть **ключ выдаёт магазин**, а manifest подстраивают под него. Мы в фазе 1 сделали наоборот: сгенерировали свою RSA-пару и зафиксировали ID `ilcnkoocagmcjikbelobkiflaplolbak` (приватный ключ в `.keys/`), а redirect URI OAuth зарегистрировали на него.

**Отсюда порядок для публикации:**
1. создать элемент в консоли и загрузить сборку **черновиком, не публикуя** — ID появляется на этом шаге, до релиза;
2. зарегистрировать в OAuth-приложении Shikimori redirect URI `https://<ID из консоли>.chromiumapp.org/` (старый оставить, пока живут локальные установки);
3. вписать в `WXT_MANIFEST_KEY` публичный ключ из вкладки Package и пересобрать;
4. проверить вход на сборке с новым ключом **до** публикации;
5. собрать архив **без ключа** (`WXT_MANIFEST_KEY=none pnpm zip`) и публиковать его.

Пятый пункт — не описка. Ключ нужен ровно распакованной локальной сборке, чтобы её ID совпал с магазинным и OAuth ушёл на зарегистрированный redirect URI; в загружаемом архиве это же поле — причина отказа (см. выше). Сборок две, и путать их нельзя.

**Фактические значения (2026-08-05):** элемент создан, Item ID `bpjembchapdbgncmacpkbepfjghjdkan`, ключ магазина лежит в `.env`; проверено, что ID выводится из этого ключа (SHA-256 от DER, первые 16 байт, `0-f → a-p`). Старый ID `ilcnkoocagmcjikbelobkiflaplolbak` и его redirect URI остаются зарегистрированными, пока живут локальные установки.

**Проверено 2026-08-05 первой же загрузкой: консоль пакет с нашим `key` не принимает** — форма отвечает «Недопустимое поле в файле манифеста: key» и файл не берёт. Значит порядок безальтернативный: черновик собирается командой `WXT_MANIFEST_KEY=none pnpm zip`, ключ возвращается уже магазинным на шаге 3. ### `client_secret` в бандле — решение принято 2026-08-06
Найдено 2026-07-29 при работе над фазой 8 как блокер подачи. **Принято 2026-08-06** — де-факто публикацией: расширение вышло в магазин на приложении №2175, то есть выбран вариант 2 из списка ниже, а публичность секрета принята сознательно. Разбор угрозы оставлен как есть: он объясняет, чем именно эта цена ограничена.

`docs/04-auth.md` §5 разрешает держать секрет в собранном коде с явной оговоркой: «для личного некоммерческого проекта риск приемлем; максимум — кто-то сможет представляться нашим приложением». **Публикация отменяет эту предпосылку** — бандл из магазина скачивает кто угодно, и секрет приложения №2175 перестаёт быть секретом. README это признавал прямым текстом («Публиковать такую сборку не следует», §3), то есть файл сам себе противоречил после решения публиковаться; оговорка убрана 2026-07-30 (чекбокс в фазе 9).

Что именно под угрозой и что нет:
- **не утекают** токены и данные пользователей — секрет не даёт доступа к чужим аккаунтам;
- **утекает личность приложения**: обмен кода на токен можно проводить от имени ShikiFAV. Обмен требует кода, выданного на зарегистрированный redirect URI, поэтому сценарий не тривиален — но лимиты, репутация и сама регистрация приложения на Shikimori висят на владельце.

**Насколько велика угроза на самом деле (уточнено 2026-07-30).** Секрет в одиночку почти ничего не даёт. Обмен кода на токен требует кода, а он выдаётся только на **зарегистрированный** redirect URI, то есть на `https://<ID расширения>.chromiumapp.org/`; принять его, не владея расширением с этим ID, нельзя. Зарегистрировать свой redirect URI нельзя без доступа к аккаунту владельца на Shikimori. Обновить чужой токен нельзя без самого refresh-токена из браузера пользователя. Остаётся возможность представляться приложением в служебных запросах — риск репутации и лимитов, а не доступа к чужим аккаунтам.

Варианты, по убыванию предпочтительности:
1. **Попросить Shikimori включить приложению режим public client (PKCE без секрета).** Единственный вариант, который убирает секрет, а не смягчает последствия. В фазе 1 живая проба дала 401 `invalid_client`, то есть аутентификация клиента у приложения №2175 сейчас обязательна, при этом `code_challenge` на `/oauth/authorize` уже принимается — просьба узкая: разрешить помечать приложение публичным. Черновик запроса готов, docs/04 §5. `PKCE_ENABLED` в коде реализован. **Остаётся открытым и после публикации:** запрос отправляет владелец, к срокам и фазам он не привязан; ответ «да» уберёт секрет из сборки, и тогда правятся docs/04 §5 и абзац README §3.
2. **Опубликовать на приложении №2175, добавив в него третий redirect URI** — с ID, который выдал магазин (два, dev и prod, там уже были зарегистрированы). **Принято 2026-08-06 — так и сделано.** Секрет при этом публичен, и это принято сознательно: см. оценку угрозы выше. README и docs/04 §5 переписаны под это ещё 2026-07-30, факту публикации они не противоречат.
3. **Отдельное приложение под магазинную сборку.** Раньше стояло выше как рекомендация — **понижено 2026-07-30 после разбора.** Покупает только изоляцию: блокировка публичного приложения не задевает личную установку, и секрет магазинной версии можно перевыпустить отдельно. Стоит второго имени приложения — а имя уходит в `User-Agent` каждого запроса (правило 3 CLAUDE.md), то есть двух `.env`, двух регистраций и развилки в сборке. Брать, только если изоляция личной установки важна сама по себе.

**Отдельно про «перевыпустим секрет, если утечёт».** Это не дешёвая операция после публикации: смена секрета ломает обновление токенов у всех, кто уже поставил расширение, до того как до них дойдёт новая версия — то есть означает принудительный повторный вход у всех пользователей. Планировать компрометацию как рутину нельзя ни в одном из вариантов.

Вариант выбран, и тексты под него уже написаны: README §3 и docs/04 §5 говорят, что именно значит секрет в бандле и чем ограничен риск. Рассогласования между ними и фактом публикации нет.
