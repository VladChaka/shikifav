### Правки по итогам просмотра владельцем (2026-07-27/28)

**Решения, принятые за владельца (отменяются дёшево):** потеря фокуса **отменяет** ввод, а не сохраняет — popup закрывается от любого клика мимо, и сохранение по blur молча записало бы недонабранное «1» вместо «11»; ввод доступен **при любом статусе**, в отличие от `[+1]` (только «Смотрю»/«Пересматриваю») — отметить, где остановился, нужно и в «Отложено», и в «Брошено».

**Реализация:** кликается вся фраза `5 / 11 эп.` (мишень 55,8×20,8 против 7,6 у одной цифры), полем становится только число, `/ 11 эп.` остаётся текстом и подменяется на «макс. N» при недопустимом значении. Высота строки в наборе не меняется (замер: 79,00 → 79,00). `[+1]` и ввод делят `runRowAction`, поэтому блокировка строки, откат и тост — те же; реконсиляция серверного ответа вынесена в общую `applyProgressResult()`.

**DoD дополнения (ручной smoke владельца):** введённое число видно на сайте; на последней серии поведение то же, что у `[+1]`; недопустимое значение не уходит на сервер; ввод в строке манги двигает главы.

**Поведение на последней серии уточнилось по ходу дополнения (2026-07-29), формулировка DoD приведена к факту.** Исходно тут стояло «на последней серии появляется предложение перевести в „Просмотрено“». На аниме с известным числом серий такого предложения **не бывает**: Shikimori переводит тайтл в «Просмотрено» сам (docs/03, проверено PATCH), а `maybeSuggest` (`src/composables/use-lists.ts`) ставит предложение только по **подтверждённому сервером** статусу `watching`/`rewatching` — к моменту ответа он уже `completed`. Предложение остаётся живым там, где сервер сам не переводит (например, прогресс догнали, а статус не сменился). Смена статуса сервером показывается тостом — Ф7-20, тот же факт записан выше в чекбоксе дополнения и ниже в smoke.

2. вкладка **Package** → **View public key** → скопировать содержимое между `-----BEGIN PUBLIC KEY-----` и `-----END PUBLIC KEY-----`, убрать переносы строк;
3. вписать это значение в манифест как поле `key` — тогда локальная сборка получает **тот же ID, что и элемент магазина**;
4. сверить: ID на `chrome://extensions` должен совпасть с Item ID в консоли.

То есть **ключ выдаёт магазин**, а manifest подстраивают под него. Мы в фазе 1 сделали наоборот: сгенерировали свою RSA-пару и зафиксировали ID `ilcnkoocagmcjikbelobkiflaplolbak` (приватный ключ в `.keys/`), а redirect URI OAuth зарегистрировали на него.

**Отсюда порядок для публикации:**
1. создать элемент в консоли и загрузить сборку **черновиком, не публикуя** — ID появляется на этом шаге, до релиза;
2. зарегистрировать в OAuth-приложении Shikimori redirect URI `https://<ID из консоли>.chromiumapp.org/` (старый оставить, пока живут локальные установки);
3. вписать в `WXT_MANIFEST_KEY` публичный ключ из вкладки Package и пересобрать;
4. проверить вход на сборке с новым ключом **до** публикации;
5. собрать архив **без ключа** (`WXT_MANIFEST_KEY=none pnpm zip`) и публиковать его.

Пятый пункт — не описка. Ключ нужен ровно распакованной локальной сборке, чтобы её ID совпал с магазинным и OAuth ушёл на зарегистрированный redirect URI; в загружаемом архиве это же поле — причина отказа (см. выше). Сборок две, и путать их нельзя.

**Фактические значения (2026-08-05):** элемент создан, Item ID `bpjembchapdbgncmacpkbepfjghjdkan`, ключ магазина лежит в `.env`; проверено, что ID выводится из этого ключа (SHA-256 от DER, первые 16 байт, `0-f → a-p`). Старый ID `ilcnkoocagmcjikbelobkiflaplolbak` и его redirect URI остаются зарегистрированными, пока живут локальные установки.

**Проверено 2026-08-05 первой же загрузкой: консоль пакет с нашим `key` не принимает** — форма отвечает «Недопустимое поле в файле манифеста: key» и файл не берёт. Значит порядок безальтернативный: черновик собирается командой `WXT_MANIFEST_KEY=none pnpm zip`, ключ возвращается уже магазинным на шаге 3. Такая сборка входить не умеет — она нужна ровно для того, чтобы магазин выдал ключ.

**Подготовлено 2026-07-30 (за ассистентом ничего не осталось):** ключ вынесен из литерала в `wxt.config.ts` в переменную `WXT_MANIFEST_KEY` (`.env`), правило выбора — `src/lib/manifest-key.ts`, под тестами. Три случая: значение → ключ в манифесте; `none` → сборка без ключа (шаг «если откажет» выше) плюс предупреждение в консоль; пусто или переменной нет → сборка падает. ## Фаза 11 — Уведомления и бейдж (US-12) — В РАБОТЕ с 2026-08-17

Взята после двенадцатой: пропуск 2026-08-10 был отсрочкой, а не отменой, и номер за пунктом сохранялся именно на этот случай (см. врезку в разделе фазы 12).

**Четыре решения владельца 2026-08-17, принятые ДО декомпозиции** (каждое — из трёх проработанных вариантов, разбор — в отчёте разведки фазы):

1. **Бейдж и уведомления идут одной фазой.** Планировщик, снимок, гарды по токену и вся фоновая обвязка общие для обеих половин, поэтому разрез экономил бы одну UI-задачу, но платил вторым полным проходом ревью магазина — самой длинной и наименее управляемой частью работы.
2. **`alarms` — обязательный permission, `notifications` — по кнопке (`optional_permissions`).** Chrome документирует: permission с предупреждением добавляется в обновление ценой отключения расширения у каждого, кто его уже поставил, до явного согласия («the extension will be disabled until the user accepts the new permission», developer.chrome.com/docs/extensions/develop/concepts/permission-warnings). Предупреждение из двух наших разрешений даёт ровно одно — `notifications` («Display notifications», permissions-list); у `alarms` предупреждения нет. Значит, UI-веткой платим ровно за то разрешение, которое реально угрожает установленной базе, а бейдж работает у всех сразу после обновления.
3. **Число на бейдже — это тайтлы с невзятыми вышедшими сериями**, а не сумма серий и не «новое с прошлого визита». Единственная семантика, которая физически не может разойтись со строкой календаря «вы на 5-й из 8 вышедших» и не требует правил сброса и очистки при смене аккаунта. Сумма серий на аккаунте с бэклогом горела бы трёх-четырёхзначным числом постоянно и читалась бы как поломка; почтовая семантика показывала бы 0 при трёх невзятых сериях в календаре.
4. **Одно уведомление на тайтл, по всем трём статусам календаря** («Смотрю», «Пересматриваю», «Запланировано»). Аргумент, который в фазе 7 уже отменил исключение «Запланировано», действует и здесь: серверный `status: "ongoing"` сам отсекает анонсы, а на аккаунте владельца онгоинги лежали ровно в «Запланировано» — без этого статуса функция промолчала бы у самого владельца.

**Ещё два решения владельца 2026-08-17, по итогам дизайн-карточек Ф11-4:**

5. **Функция включена по умолчанию.** Иначе бейдж после обновления не появится ни у кого, а DoD фазы обещает обратное. Следствие принимается сознательно: фоновый опрос раз в полчаса включается у всех вошедших — поведения «расширение ходит в сеть без открытого popup» у нас до сих пор не было вовсе, и оно обязано быть описано в PRIVACY.md и docs/07 прямым текстом (Ф11-12).
6. **У уведомлений свой ряд чипов, отдельно от счётчика.** Один переключатель на обоих означал бы, что уставший от уведомлений гасит заодно и счётчик. Назойливость — единственная причина, по которой такую функцию выключают целиком, и лечить её ценой счётчика неправильно. Ряд уведомлений подчинён ряду счётчика: без опроса уведомлений не бывает, поэтому у него есть состояние «недоступно, счётчик выключен».

**Решения, принятые за владельца (отменяются дёшево).**
- **Факт «вышла серия» берём диффом `episodesAired` по сохранённому снимку**, а не из REST-фида `/api/topics/updates`. Фид дал бы точный номер серии, время события и событие `released`, но это второе место, где правило 5 CLAUDE.md («чтение — GraphQL») перестаёт быть безусловным, — и дока Shikimori сама рекомендует GraphQL. Отменяется добавлением одного источника, не переписыванием фазы.
- **Период опроса — 30 минут одной константой, без настройки.** Лаг между слотом эфира и появлением серии в БД сам по себе имеет медиану ~46 мин (замер n=14, 2026-08-17), поэтому более частый тик покупает точность, которой в данных нет. Цена по лимитам нулевая: 1–3 запроса в тик — это ≤0,2 rpm из наших 80.
- **Будильник по `nextEpisodeAt` не используется даже как оптимизация:** даты нет у 38% онгоингов на трёх страницах выдачи, а у остальных данные обновляются позже слота (хвост до 10,7 ч) — периодический опрос всё равно понадобился бы страховкой.
- **Опрос идёт своим узким запросом**, а не переиспользованным `listCalendar()`: `id, name, russian, url, episodesAired, nextEpisodeAt, userRate{id,episodes}` — **12,7 КБ на 50 строк против 25,2 КБ** у календарной формы (перезамер 2026-08-17 после правок ревью; первая пара 4,6/28,2 не воспроизводится — список онгоингов на сервере другой, docs/03). Цена — второй литерал `mylist`; он снят: оба запроса собираются из одной константы `ONGOING_ANIMES_FILTER`, и тест сверяет аргументы двух отправленных запросов посимвольно.
- **Нет `auth` в storage → тик пропускается до сети.** Иначе разлогиненный пользователь каждые полчаса платит отказом, а при истёкшем токене ещё и refresh-запросом.

**Границы фазы.**
- **Новых сетевых адресатов нет**, `host_permissions` не меняются. Новыми становятся ровно `alarms` (обязательный) и `notifications` (по кнопке).
- **Фон остаётся read-only**, как календарь в фазе 7: кнопки «Отметить серию» в уведомлении нет — иначе фаза тянет оптимистику, откат и реконсиляцию, а сообщить об ошибке из уведомления некуда.
- **«Вышла последняя серия» не обещаем.** Под фильтром `status: "ongoing"` финал сезона систематически не наблюдается: 0 из 150 онгоингов имеют `episodesAired ≥ episodes`, при этом среди 50 released сезона 2026 у 7 `episodesAired` так и не дошёл до `episodes` (замер 2026-08-17). Тайтл уходит из выдачи опроса раньше, чем счётчик догоняет общее число серий.
- **Фаза anime-only**, как и календарь: у `Manga` нет ни `nextEpisodeAt`, ни `episodesAired`.

**Риск, который фаза обязана закрыть кодом.** Неудачный refresh внутри фонового тика вызывает `clearAuth()`, а тот сносит `auth` **и весь session-кэш** (`lastSearch`, `lastTab`, `lastCalendar`) — то есть фон способен молча разлогинить пользователя без единого кадра на экране. **Известное ограничение, принятое вместе с решением 4.** Дифф `episodesAired` не отличает «вышла серия» от «тайтл только что добавлен в список»: первый опрос после добавления показал бы N новых серий разом. Лечится тихим посевом снимка (Ф11-6), а не уведомлением. Отдельный наблюдённый случай — несколько серий за один тик (id 61649: серии 1 и 2 с разницей в 2 минуты), поэтому текст уведомления обязан переживать диапазон, а не только «+1».

**Второе известное ограничение — откат счётчика на сервере (найдено ревью ядра 2026-08-17).** Если Shikimori поправит данные вниз, а потом вернёт обратно (N → N−1 → N), пользователь получит уведомление о серии, которая уже выходила. Снимок на откате берёт **меньшее** значение сознательно: альтернатива — держать большее — молча съела бы СЛЕДУЮЩУЮ настоящую серию, а это хуже ложного срабатывания. Ограничение закреплено тестом (`aired-snapshot.test.ts`) и названо здесь, потому что владелец согласовывал «одно уведомление на тайтл», а не «уведомление на откат данных Shikimori».

**Бейдж считает и «Запланировано» — решение по итогам ревью ядра 2026-08-17.** Счётчик статус-агностичен: в выдаче опроса статуса списка нет вовсе, а тайтл из «Запланировано» с вышедшими сериями — это ровно «ждёт». Цена: у «Запланировано» в календаре **нет** строки отставания («собираюсь смотреть» не может отставать), поэтому критерий US-12 приведён к факту — счётчик и календарь совпадают по составу тайтлов, а не по наличию подписи в строке.

**Потолок уведомлений за тик — правка по аудиту 2026-08-17, отступление от решения 4.** Цикл по приростам был без ограничения: до 150 уведомлений (`ONGOING_LIMIT` 50 × `ONGOING_MAX_PAGES` 3). Сценарий обычный, а не экзотический — ноутбук был выключен несколько дней, снимок в `storage.local` простой пережил, первый тик через минуту после старта диффит недельную разницу, и человек получает залп с названиями своих тайтлов сразу после включения машины, в том числе на общем экране. **Стало: до 3 отдельных уведомлений, по остальным приростам снимок двигается молча.** Решение 4 («одно уведомление на тайтл») этим сужается, и владелец может его вернуть — но 150 уведомлений подряд не были частью того решения.

Сводное уведомление «ещё у N тайтлов» было сделано и **снято тем же днём решением владельца**: у него нет одного тайтла, а значит и адреса, куда вести клик после того, как клик стал вести на страницу тайтла. Единственный оставшийся для него вариант — открыть расширение вкладкой — возвращал ровно то состояние, которое этим решением и убиралось. Про остальные тайтлы человек узнаёт из числа на иконке: оно ровно для этого и есть.

**Третье известное ограничение — принято, не чинится кодом (аудит 2026-08-17).** После всей санитизации заголовок уведомления остаётся произвольным ОДНОСТРОЧНЫМ текстом из API под нашей иконкой и именем «ShikiFAV»: «Frieren\nВВЕДИТЕ ПАРОЛЬ» схлопнется в одну строку, но останется на экране как сообщение от расширения. Почему не лечим: позиция, из которой это достижимо, — подменённый ответ Shikimori, то есть тот же origin, который выдаёт и проверяет Bearer. Он уже владеет аккаунтом, ради которого затевался бы фишинг, и уже управляет каждой строкой названия в поиске, календаре и списках через тот же `displayTitle`. Теперь клик ведёт на адрес **из того же подменённого ответа** — ровно поэтому в Ф11-16 появился отдельный `shikimoriHref()`, который разбирает адрес и сверяет хост со списком `ORIGINS`, а не сравнивает префикс: `https://shikimori.io.evil.example/x` проходит любой `startsWith`. Чужой хост уведомление не отменяет — оно показывается, но кликом никуда не ведёт. **Наблюдение с замера Ф11-3 ослабляет довод ещё раз:** на Linux Chrome рисует в шапке уведомления свой логотип и вовсе не показывает «ShikiFAV», то есть враждебная строка читается как сообщение от браузера. Ограничение остаётся принятым — позиция всё та же, подменённый ответ Shikimori, — но принято оно теперь с открытыми глазами.

Отвергнутая альтернатива: поменять слоты местами (наш текст в заголовок, название в тело) — она ломает то, ради чего слоты и выбраны: система обрезает только заголовок, и он узнаётся по началу, а десять уведомлений с одинаковым заголовком неразличимы.

**Название тайтла возится каждым тиком — решение архитектора 2026-08-17.** Эталонный запрос опроса не содержал `name`/`russian`, а текст уведомления обязан нести название по настройке `titleLang`. Из двух вариантов выбран первый: возить два поля всегда или добирать их вторым запросом только по тайтлам с приростом. Второй экономит трафик на тихих тиках, но заводит второй запрос ровно в тот момент, когда надо быстро показать уведомление, и путь «уведомление без названия» при его отказе. **Решение перепроверено против замера:** пара имён удваивает тик (4,2 → 9,3 КБ на 50 строк, ×2,2), но дельта пропорциональна размеру списка — 244 КБ/сутки набегают только у пользователя с полусотней онгоингов, у пользователя с тремя это ~15 КБ/сутки. Простота победила.

**DoD:** после обновления бейдж показывает число тайтлов с невзятыми вышедшими сериями и гаснет по мере отметок прогресса; включённые в настройках уведомления приходят на вышедшую серию тайтла из трёх статусов календаря и по клику открывают страницу этого тайтла на Shikimori; выключенная функция не создаёт ни одного alarm и ни одного фонового запроса; разлогиненный пользователь не порождает сетевых запросов в фоне; обновление поверх установленной версии не отключает расширение; `host_permissions` не изменились; `pnpm compile && pnpm lint && pnpm test && pnpm size` зелёные.

- Выключить «Счётчик на иконке»: число гаснет сразу; ряд «Уведомления» становится недоступным (серым) и **показывает сохранённое значение** — если там было «Включены», оно и остаётся «Включены», а не подменяется на «Выключены»; под ним строка «Уведомления недоступны: пока счётчик выключен, расширение не проверяет выход серий»; наши уведомления пропадают из системного центра (чужие остаются).

- Включить счётчик обратно: ряд уведомлений возвращается ровно в то значение, что показывал; число на иконке появляется в течение ~минуты, и **пачки уведомлений при этом не приходит** (снимок пересевается молча).
- Выключить только «Уведомления» (счётчик включён): строки состояния под рядом нет вовсе; счётчик продолжает считать и гаснуть по отметкам; уведомления не приходят ни на один эфир.
- Разлогиниться и открыть настройки: оба ряда серые, сохранённые значения на месте, строка «Нужен вход: серии считаются по вашим спискам…».

**Разрешение на уведомления**
- Кнопка «Разрешить уведомления» видна только когда включены оба ряда и разрешения ещё нет; под ней строка «Уведомления включены, но Chrome ещё не выдал разрешение…».
- Клик → системный диалог. Согласие → строка меняется на «Уведомления разрешены — Chrome покажет сообщение, когда выйдет серия», кнопка исчезает без перезагрузки страницы.
- Отказ в системном диалоге → тост «Chrome не выдал разрешение на уведомления», строка и кнопка остаются на месте, ряд не выключается сам.
- Отзыв при **открытой** вкладке настроек: снять разрешение в `chrome://extensions` (или из консоли воркера `chrome.permissions.remove({permissions:['notifications']})`) → блок на открытой вкладке сам возвращается к «…Chrome ещё не выдал разрешение…» с кнопкой. Выдать снаружи обратно — кнопка исчезает сама.
- Пока разрешения нет: счётчик работает как обычно, уведомлений нет, и расширение само у системы ничего не спрашивает.

**Приватность**
- После «Выйти» в консоли воркера: `chrome.storage.local.get(null)` — ни `airedSnapshot`, ни `badgeBacklog`; `chrome.storage.session.get(null)` — нет `airedNotificationUrls`.
- Наши уведомления убраны из системного центра (уведомления других расширений — на месте), число на иконке погасло.
- «Аккаунт и данные» → «Очистить кэш»: оба ключа (`airedSnapshot`, `badgeBacklog`) исчезли. Число на иконке при этом может остаться до следующего тика — кнопка чистит данные, а не иконку.

**Ноль запросов там, где обещано** (`chrome://extensions` → «Инспектировать service worker» → вкладка Network, вкладку не закрывать)
- Счётчик выключен: за время, когда тик был бы, ни одного запроса — будильника нет вовсе.
- Разлогинен, счётчик включён: форсировать тик → в Network пусто, ни одного обращения к Shikimori. (Сам будильник может ещё числиться в `getAll()` до следующего запуска воркера — он снимается на старте; главное здесь — пустая сеть.)
- Обычный тик на живой сессии: **1–3 запроса** GraphQL и больше ничего.
- Открытие popup по-прежнему даёт 0 запросов; вкладка «Календарь» — ровно один.

**Регресс (всё как раньше)**

- Связанные тайтлы: открываются от карточки и от строки списка, возврат и Escape работают.
- Контекстное меню и полноэкранная страница поиска.
- Настройки: тема, названия, стартовая вкладка, домен API, «Поддержать»; высота панели «Поведение» не прыгает при кликах по чипам.

**Только в smoke релиза — обновление поверх магазинной версии** (на распакованной сборке не проверяется, см. Ф11-3: `Load unpacked` выдаёт разрешения без запроса согласия)
- На профиле с установленной магазинной версией дождаться авто-обновления или нажать «Обновить» на `chrome://extensions`.
- Расширение **не отключилось**: карточка активна, нет «Требуется разрешение», нет кнопки повторного включения, нет предупреждающего значка и ошибок на карточке.

Все шесть выбраны по одному признаку — **ни одна не требует нового permission**: после публикации разрешение с предупреждением выключает расширение у всей установленной базы, и это ограничение теперь определяет, что вообще стоит рассматривать. Данные уже есть — `related` реализован фазой 12, экран связанных открывается тем же запросом. Цена: один запрос в момент перевода в «Просмотрено» и решение, где это показать (тост? строка в списке?). Новых permissions и адресатов нет. **Самая дешёвая из шести и самая заметная в ежедневном сценарии.**

Заметка пишется тем же `rates.update`, которым уже двигается прогресс, — протокол сообщений не меняется. Цена: поле ввода в строке списка (по образцу inline-ввода прогресса из дополнения фазы 7) и место под счётчик пересмотров. **Осторожно с бюджетом popup CSS** — запас 121 Б, см. отдельную задачу про `cssCodeSplit`.

- **Фаза 19 — Легальные площадки:** `Anime.externalLinks` есть в схеме (интроспекция 2026-08-17), но его форма **не разбиралась** — первым делом интроспекция поля и замер, влезает ли оно в карточку по complexity 190. Ссылки внешние, гард `httpsHref` уже написан, permissions не нужны. Риск: среди ссылок могут быть площадки, которых не хочется показывать, — понадобится правило отбора, и это решение владельца, а не архитектуры.
- **Фаза 20 — Сортировка «Моих списков» по недавно изменённым:** сейчас список читается через `animes(mylist:)`, и `OrderEnum` там сортирует по полям **тайтла**, а не вашей записи. Нужная сортировка живёт в корневом `userRates(order: {field: updated_at})` — это **второй путь чтения**, и у него `status: UserRateStatusEnum` принимает одно значение, а не список через запятую (в отличие от `MylistString`), то есть «Смотрю» + «Пересматриваю» = два запроса. - **Фаза 21 — Экспорт списков файлом:** резервная копия без всякого MAL. **Permission `downloads` не нужен** — в странице расширения файл отдаётся через blob и `<a download>`; у `downloads` есть предупреждение, то есть он стоил бы отключения расширения у всех при обновлении.

### Рассмотрено и отвергнуто 2026-08-17 (чтобы не возвращаться)
- **Content-скрипт на самом Shikimori** (кнопки расширения прямо на страницах сайта). Выглядит естественно и отвергнуто по безопасности: именно отсутствие `content_scripts`, `web_accessible_resources` и `externally_connectable` — причина, по которой два атакующих прогона 2026-08-17 закончились нулём выживших находок. Ни веб-страница, ни другое расширение сейчас физически не дотягиваются до background. Фича открывает всю границу доверия разом, и тогда `sender`-гард в `src/lib/messaging.ts` из «защиты в глубину» становится обязательным рубежом.
- **Любая функция, требующая permission с предупреждением** — `history`, `bookmarks`, `downloads`, широкие host_permissions. После публикации такое обновление выключает расширение у каждого, кто его поставил, до явного согласия (docs/06, решение владельца 2 фазы 11). Фаза 11 прошла только потому, что у `alarms` предупреждения нет, а `notifications` удалось объявить необязательным.
- **Просмотр видео, чтение манги, комментарии, форум и клубы** — остаются не-целями docs/01. Расширение выигрывает у сайта скоростью, а не полнотой.

- **Отдельно, вне очереди — подготовка листинга Chrome Web Store:** описание, скриншоты, privacy policy, обоснование каждого permission, проверка политики о пожертвованиях. Не смешивать с продуктовыми фазами: это работа про магазин, а не про расширение.

### `client_secret` в бандле — решение принято 2026-08-06
Найдено 2026-07-29 при работе над фазой 8 как блокер подачи. **Принято 2026-08-06** — де-факто публикацией: расширение вышло в магазин на приложении №2175, то есть выбран вариант 2 из списка ниже, а публичность секрета принята сознательно. Разбор угрозы оставлен как есть: он объясняет, чем именно эта цена ограничена.

`docs/04-auth.md` §5 разрешает держать секрет в собранном коде с явной оговоркой: «для личного некоммерческого проекта риск приемлем; максимум — кто-то сможет представляться нашим приложением». **Публикация отменяет эту предпосылку** — бандл из магазина скачивает кто угодно, и секрет приложения №2175 перестаёт быть секретом. README это признавал прямым текстом («Публиковать такую сборку не следует», §3), то есть файл сам себе противоречил после решения публиковаться; оговорка убрана 2026-07-30 (чекбокс в фазе 9).

Что именно под угрозой и что нет:
- **не утекают** токены и данные пользователей — секрет не даёт доступа к чужим аккаунтам;
- **утекает личность приложения**: обмен кода на токен можно проводить от имени ShikiFAV. Обмен требует кода, выданного на зарегистрированный redirect URI, поэтому сценарий не тривиален — но лимиты, репутация и сама регистрация приложения на Shikimori висят на владельце.

**Насколько велика угроза на самом деле (уточнено 2026-07-30).** Секрет в одиночку почти ничего не даёт. Обмен кода на токен требует кода, а он выдаётся только на **зарегистрированный** redirect URI, то есть на `https://<ID расширения>.chromiumapp.org/`; принять его, не владея расширением с этим ID, нельзя. Зарегистрировать свой redirect URI нельзя без доступа к аккаунту владельца на Shikimori. Обновить чужой токен нельзя без самого refresh-токена из браузера пользователя. Остаётся возможность представляться приложением в служебных запросах — риск репутации и лимитов, а не доступа к чужим аккаунтам.

Варианты, по убыванию предпочтительности:
1. **Попросить Shikimori включить приложению режим public client (PKCE без секрета).** Единственный вариант, который убирает секрет, а не смягчает последствия. В фазе 1 живая проба дала 401 `invalid_client`, то есть аутентификация клиента у приложения №2175 сейчас обязательна, при этом `code_challenge` на `/oauth/authorize` уже принимается — просьба узкая: разрешить помечать приложение публичным. Черновик запроса готов, docs/04 §5. `PKCE_ENABLED` в коде реализован. **Остаётся открытым и после публикации:** запрос отправляет владелец, к срокам и фазам он не привязан; ответ «да» уберёт секрет из сборки, и тогда правятся docs/04 §5 и абзац README §3.
2. **Опубликовать на приложении №2175, добавив в него третий redirect URI** — с ID, который выдал магазин (два, dev и prod, там уже были зарегистрированы). **Принято 2026-08-06 — так и сделано.** Секрет при этом публичен, и это принято сознательно: см. оценку угрозы выше. README и docs/04 §5 переписаны под это ещё 2026-07-30, факту публикации они не противоречат.
3. **Отдельное приложение под магазинную сборку.** Раньше стояло выше как рекомендация — **понижено 2026-07-30 после разбора.** Покупает только изоляцию: блокировка публичного приложения не задевает личную установку, и секрет магазинной версии можно перевыпустить отдельно. Стоит второго имени приложения — а имя уходит в `User-Agent` каждого запроса (правило 3 CLAUDE.md), то есть двух `.env`, двух регистраций и развилки в сборке. Брать, только если изоляция личной установки важна сама по себе.

**Отдельно про «перевыпустим секрет, если утечёт».** Это не дешёвая операция после публикации: смена секрета ломает обновление токенов у всех, кто уже поставил расширение, до того как до них дойдёт новая версия — то есть означает принудительный повторный вход у всех пользователей. Планировать компрометацию как рутину нельзя ни в одном из вариантов.

Вариант выбран, и тексты под него уже написаны: README §3 и docs/04 §5 говорят, что именно значит секрет в бандле и чем ограничен риск. Рассогласования между ними и фактом публикации нет.
